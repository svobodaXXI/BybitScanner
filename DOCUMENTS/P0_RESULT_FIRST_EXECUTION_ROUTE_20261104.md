# P0 — кратчайший путь к наблюдаемому результату (решение владельца 04.11.2026)

**Статус:** предложение к существующему P0 из `DOCUMENTS/BACKLOG.md`; не новая очередь, не новый runtime-допуск и не замена контрактам `AGENTS.md`, `ASSISTANT_PROTOCOL.md`, `PAPER_CONTOUR_INTERNAL_CONSOLIDATION_PLAN_20261027.md`. При расхождении приоритет — текущая команда владельца, факты runtime и действующие защитные контракты.

## Цель и критерий направления

Главный измеримый результат: единый отказоустойчивый PAPER-контур с безопасным монолитным start/stop/update (Backend, Scanner, Robot, MIRROR, Autopilot, Telegram), без осиротевших Robot-сделок, зависших обязательств, неконтролируемого нового входа и ручной цепочки восстановления. Затем — пользовательская приёмка Telegram/Editor/графиков и фактическая PAPER-оценка торговли. CI, PR, SSH и deployment — средства, не самостоятельные победы.

**Порядок текущих зависимостей (не переставлять ради удобства):**

1. **Закончить только уже разрешённую прерванную recovery-транзакцию.** Целевой SHA `4090641514b8f558a0054fd577b2750b944fd8d6`, возобновление **только** от сохранённого и повторно аутентифицированного `backend-exited` receipt. Последний сообщённый факт: `handoff-attempt` + `backend-exited` существуют; Backend `failed`/`MainPID=0`, listener 8765 отсутствует; Telegram active, старый installed `f100ef369a1105443332b5729b558464c27be48f`; `telegram-attempt`, `handoff-proven` и upgrade не выполнялись. Это исторический отчёт, **не свежая аттестация**. Исполнитель Codex получил разрешённое задание, но его результат после потери интернет-соединения **неизвестен**. До получения свежего фактического отчёта **не запускать второй исполнитель/дублирующий переход, не повторять SIGINT/exceptional handoff/canonical STOP**. При неясности — fail closed. Разрешено только точное продолжение в границах уже выданного владельцем допуска и при всех штатных gates. Не создавать обходной GitHub execute.

2. **Фактическая приёмка EDITOR_ONLY после recovery**, только если шаг 1 завершён доказанно. Installed/running exact SHA; Backend active, Telegram ready; Scanner STOPPED, Autopilot OFF; PAPER DB identity/integrity сохранены; отсутствие торговых операций, one-shot receipts неизменны. Затем один реальный Telegram → Editor тест открытия и сохранения геометрии. Доступность сервисов сама по себе не доказывает работоспособность редактора. Если шаг 1 BLOCKED, сначала устранить только подтверждённую узкую причину в GitHub (PR + targeted regression), не инициируя новый runtime-переход без отдельного разрешения.

3. **Вернуться к владельческому P0 — монолитному PAPER lifecycle**, используя уже реализованные admission freeze/drain/quiescence, Robot/STOP/TAKE, one-shot receipts, immutable release и canonical reconciliation. Довести один цельный start/stop/update до наблюдаемого результата на VPS по отдельному runtime-допуску. Без раскладывания freeze, drain, JASMY handoff, upgrade и reconciliation на самостоятельные владельческие квесты. JASMY Flat при OPEN Robot trade, pending LIMIT, protection obligations и race с PAPER_AUTO — обязательные проверяемые границы, а не повод для их обхода.

4. **Потом — продуктовые проблемы и торговые метрики:** корректные Telegram/MIRROR карточки и графики, геометрия в Editor, повторные входы, затем сравнение сигналов, исполнений, STOP/TAKE и net PnL на доказанных PAPER циклах. Не считать инфраструктурные исправления торговой приёмкой.

## Улучшение исполнения

- **Одна цель → одно ограниченное поручение → одно наблюдаемое постусловие.** В запросе исполнителю описывать end state, запреты, достаточные проверки, STOP boundary; не расписывать владельцу серию микрокоманд. Код и PR — через GitHub; Codex — только для согласованных VPS действий.
- **На каждом BLOCKED:** зафиксировать фазу, durable receipts и точную причинную границу; не повторять необратимую операцию. Устранение — минимальным патчем с регрессионным тестом для реального CLI/entrypoint, а не только внутренних helper-функций. Не расширять scope.
- **Минимум повторов:** переиспользовать подтверждённые GitHub/CI evidence и сохранённые receipts, но всегда заново проверять динамические runtime gates перед действием. Для владельца — только один действительно необходимый approval в момент защищённого перехода.
- **SSH/GitHub-мост к VPS:** после закрытия текущей recovery рассмотреть уже существующий защищённый GitHub-механизм и возможность обслуживать VPS без зависимости от домашнего ПК. Это **отдельное условное P1-улучшение**, а не причина откладывать P0 или право на произвольный remote execute. До проектирования установить текущие разрешения, безопасность секретов и одноразовых токенов, audit trail, scoped allowlist, human approval для мутаций, fail-closed и гарантии against duplicate execution. Не создавать новый постоянный привилегированный канал без необходимости и разрешения.
- **Связь/исполнитель:** потеря интернета или отсутствие отчёта не доказывают ни отсутствие выполнения, ни успех. Сначала выяснить фактическое состояние исходной one-shot транзакции, затем решать следующий шаг. Никаких параллельных оркестраторов на одном переходе.

## Неизменяемые ограничения

Без нового разрешения — никаких изменений VPS/runtime/PAPER DB; никогда не обходить STOP/TAKE, admission, reconciliation, one-shot receipts, position/order ledger. Запрещены LIVE, raw Market, ручной SQLite repair, повтор SIGINT или canonical STOP. Статусы `READY`, `SAFE`, `COMPLETE` только при актуальных доказательствах. XP/достижения — лишь за верифицированный пользовательский результат, не за документ или PR.

**Сразу следующий факт, который требуется:** итог единственного уже отправленного Codex continuation (точные postconditions или BLOCKED с фазой). Переход к следующей фазе — только после него.
