## 1. Главный измеримый результат

Перестать повторять убыточную торговую логику Робота и добиться доказанного улучшения **net P&L в защищённом PAPER**, а не показной готовности PR/интерфейса. Общий цикл:

1. **Статистика:** найти фактическую убыточную PAPER-сделку, её точный ID, реальный паттерн (только доказанная атрибуция), свечи и исполнения с комиссиями.
2. **Локальный Симулятор:** открыть именно этот ID, восстановить *как было*, отдельно исследовать альтернативные входы/выходы/STOP/безубыток и точно отделить реальные PAPER-события от виртуальных и условных L2-исполнений.
3. **Scanner/Robot:** по проверенной причине убытка исправить узкую границу — геометрию сигналов, детектор, вход, риски, STOP/безубыток/reentry либо импульсный вход по потоку ордеров/стакану.
4. **Доказательство:** сравнить baseline и исправление на одинаковых данных; независимый holdout, комиссии, проскальзывание, просадка, частичные исполнения; затем **только отдельно разрешённый** безопасный PAPER-runtime pass.
5. Цикл повторяется по фактическим убыточным сделкам; сторонние UI-идеи и инфраструктура без прямого влияния на результат ставятся в очередь.

Нет цели «гарантировать прибыль»: итоговое улучшение принимается по независимым данным и защищённому PAPER, а не по одной прибыльной ночи или заранее подогнанному симулятору. LIVE запрещён.

## 2. Целевая структура — не более трёх рабочих чатов

Пока структура **планируется**, а не считается выполненным переносом. Имена можно утвердить/уточнить после handoff. Каждый компонент имеет одного **писателя**, остальные потребляют контракт.

Один принимающий ответственный за frontend и replay; миграция с прежних 2+ чатов только после их handoff. | Торговый Scanner/Robot runtime, основную реализацию стратегий, VPS release/SSH |
| **SCANNER_ROBOT — «Scanner и Robot»** | Редактор исправленных сигналов, H1/M5 геометрия/приор, Wedge/Mirror/Box, детекторы, торговые решения, L2/«охота за импульсом», вход, STOP/TAKE, безубыток, reentry, shared trading core. **Особые пересечения:** `DiaryOverlay.tsx/.css/.test.tsx` — только ANALYSIS; `ReplayPage.tsx`, `RunSetupPanel.tsx`, `research/local_replay_viewer` — только ANALYSIS; shared Scanner/Robot detection/risk/STOP implementation — только SCANNER_ROBOT; `tools/windows_vps_manager.py`, `tools/vps_owner_control.py`, `tools/paper_maintenance.py` — только MONOLITH. Изменение общего API/контракта может потребовать второго трека, но сначала один владелец и согласованный interface handoff. Не создавать две расходящиеся версии стратегии — Simulator импортирует/переиспользует существующий shared core через разрешённую изолированную execution boundary.

## 4. Живой журнал вместо конкурентной перезаписи Markdown

Все активные чаты обязаны **читать план и последние релевантные комментарии [#1077](https://github.com/svobodaXXI/BybitScanner/issues/1077) до новой работы**. По новым проверенным фактам чат оставляет один компактный комментарий в issue:

```text
TRACK=ANALYSIS|SCANNER_ROBOT|MONOLITH
CHAT=<текущее название>
TASK=<один конечный результат + ссылка PR/issue>
STATE=CLAIMED|IN_PROGRESS|CODE_READY|MERGE_AUTH_REQUIRED|MERGED|RELEASE_QUEUED|DEPLOY_AUTH_REQUIRED|DEPLOYED_VERIFIED|ACCEPTANCE_PENDING|ACCEPTED|BLOCKED|HANDOFF|READY_FOR_ARCHIVE
FILES=<точные paths или публичные API>
EVIDENCE=<текущий PR HEAD, CI, installed SHA/receipts, если проверены>
DEPENDENCIES=<внешний необходимый контракт либо none>
NEXT=<одно объективно необходимое действие>
```

Не дублировать новые документы/issue и не писать комментарии после каждой мелкой проверки. Обновление требуется **при начале действительно новой задачи, конфликте, значимом изменении PR, блокере, слиянии, авторизованной публикации, приёмке и передаче**. GitHub issue — журнал intent/state, **не mutex, не источник разрешений**; перекрёстный diff/HEAD/checks сверять перед каждым PR и merge. Если другой чат уже занят тем же файлом/концепцией — прекратить конкурирующую правку и предложить одну передачу/зависимость в #1077.

## 5. Как самостоятельно определять готовность PR, слияния, публикации

- **CODE_READY:** точный текущий PR HEAD, просмотр diff на конфликт зон, применимые checks **success**. Draft, failing/unknown checks или неразрешённый контракт → не CODE_READY.
- **MERGE_AUTH_REQUIRED:** код пригоден, но нет подтверждённого разрешения владельца на merge; чат делает read-only review и запрашивает лишь необходимое согласие **один раз**. Запись в #1077 и разрешение другому чату не подменяют owner approval. При уже данном действующем точном разрешении и отсутствии дрейфа HEAD/CI разрешено исполнить штатный GitHub merge.
- **MERGED:** GitHub merge result и commit действительно включён в соответствующий `stable`; только тогда можно перейти к RELEASE_QUEUED. Нельзя «автоматически» публиковать на VPS за счёт merge.
- **DEPLOY_AUTH_REQUIRED:** MONOLITH сверяет целевой stable SHA, bundle, installed SHA, состояние PAPER, exposed positions/STOP/TAKE, approved operating mode; требуется явное отдельно применимое разрешение владельца и preflight. Остальные чаты не проводят VPS rollout и не заставляют владельца запускать параллельные команды.
- **DEPLOYED_VERIFIED:** точный installed provenance + protected receipts + реальные API/UI postconditions. Успешный SSH, `systemd active/exited`, submit UUID, GitHub CI или отсутствие ошибок **недостаточны**.
- **ACCEPTED:** отдельная предметная приёмка — визуальная проверка графиков, точный replay/сквозная PAPER-сделка, net P&L, если релевантно. Код и установка сами по себе не принимаются за продуктовый результат.
- **BLOCKED:** указать узкую доказанную причину и единственное действие; не начинать patch/test/SSH loop без нового сигнала.
- Нельзя активировать LIVE, менять PAPER DB, обходить STOP/TAKE/admission, инициировать торговлю или скрывать unknown состояния.

## 6. Упразднение лишних чатов — только после завершения текущего ограниченного этапа

**Не ждать завершения всех идей/backlog и не закрывать чат во время незавершённого PR.** Каждый действующий чат:
1. Выясняет собственную активную узкую задачу; доводит её до ближайшей проверяемой точки (**CODE_READY/MERGED/ACCEPTED** либо честного **BLOCKED**). Зависимые merge/deploy/runtime операции без разрешений не выполняет. Если блокер вне области чата — подготавливает непрерывный handoff, а не застревает.
2. Записывает в #1077 исходный чат, PR HEAD/base, state, нерешённые дефекты, исполняемые контракты/файлы, acceptance boundary, назначенный принимающий трек, одно следующее действие.
3. Получающий трек **явно подтверждает принятие** в #1077, проверяя HEAD/ownership и отсутствие конфликтующего исполнения.
4. Только после двухстороннего handoff исходный чат пишет владельцу **«READY_FOR_ARCHIVE — текущая работа доведена до точки передачи, все незавершённые обязательства приняты таким-то треком»** со ссылкой на комментарий. Владелец сам решает закрыть/переименовать чат; никто не закрывает его автоматически и не выдаёт просьбу об архивировании за технический успех.
5. Оставшиеся три чата получают утверждённые владельцем постоянные названия и новую очередь **только после согласования фактического состава**. Не переименовывать текущие чаты до решения владельца.

**Предварительные кандидаты:** «Интерфейс Статистики» + «Статистика и графики сделок» — один владелец ANALYSIS; «Локальная Машина времени» тоже может перейти в ANALYSIS **после принятия PR #1076**, но не закрывать её с открытым необслуживаемым PR. Нужен отдельно установленный существующий ответственный за SCANNER_ROBOT, прежде чем реально сократить всё до трёх чатов. Параллельная разработка этого направления без назначенного владельца не начинается.

## 8. Иерархия и поддержка этого документа

**Приоритет авторитетов:** текущее явное решение владельца → конкретные owning technical spec/ChangeRequest и актуальный `DOCUMENTS/BACKLOG.md` → runtime/GitHub evidence → `DOCUMENTS/PROJECT_STATE.md` / `DOCUMENTS/QUEST_STATE.md` → этот координационный план и issue как **маршрутизация**, а не новый торговый норматив. `AGENTS.md` остаётся точкой входа для агентов. Этот файл изменять **только при изменении целей, владельцев или правил очереди**, через GitHub PR; ежедневный статус — в #1077 без одновременных правок файла несколькими чатами.

**Главный KPI:** меньше ручных сообщений/команд владельца до проверенного результата и доказанное улучшение защищённого PAPER net P&L, а не количество PR, документации, тестовых запусков или набранных XP. Не создавать отдельный «координационный рейд» ради отчётов.
