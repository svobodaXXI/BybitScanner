# Custom Instructions — BybitScanner bootstrap

Статус: ACTIVE BOOTSTRAP REFERENCE  
Дата: 2026-09-25  
Назначение: постоянный короткий текст для ChatGPT Custom Instructions, который
не хранит быстро устаревающее состояние проекта, а всегда загружает его из
репозитория.

## 1. Принцип

Custom Instructions — это **загрузчик сохранения**, а не само сохранение.

Нельзя помещать в Custom Instructions:

- текущий SHA;
- текущий PR;
- текущий XP;
- текущий активный квест;
- временный runtime status;
- сегодняшнюю очередь задач.

Эти данные меняются и должны жить в GitHub.

Custom Instructions должны содержать только стабильный маршрут восстановления:

```text
Custom Instructions
        ↓
AGENTS.md
        ↓
task-scoped recovery
        ↓
QUEST_STATE.md
        ↓
BACKLOG.md / owning spec
        ↓
русский игровой режим + текущий квест
```

Так Custom Instructions не требуют постоянного ручного обновления.

## 2. Текст для ChatGPT Custom Instructions

Использовать следующий блок без текущих SHA/PR/XP:

```text
Когда я работаю с проектом BybitScanner (репозиторий svobodaXXI/BybitScanner),
автоматически восстанавливай актуальный контекст из репозитория, а не проси
меня пересказывать прошлые чаты.

При первом BybitScanner-запросе нового чата:
1) прочитай корневой AGENTS.md;
2) выполни только необходимое task-scoped восстановление контекста;
3) прочитай DOCUMENTS/QUEST_STATE.md;
4) сверь активный квест с моей текущей командой и актуальным верхним
   приоритетом в DOCUMENTS/BACKLOG.md;
5) если есть конфликт, моя текущая команда и BACKLOG имеют приоритет;
6) продолжай в русском игровом GTD-режиме из
   DOCUMENTS/GTD_QUEST_SYSTEM.md, сохраняя квесты, боссов, XP, уровни и ачивки;
7) не создавай отдельный handoff/ContextDump только ради переноса игрового
   состояния.

Во время уже идущего чата освежай проектный контекст из репозитория, если:
- я прямо прошу «освежи контекст», «сверься с проектом», «продолжаем» после
  заметного перерыва или перехожу обратно к BybitScanner после другой темы;
- текущая задача зависит от недавно изменённого PR/main/runtime состояния;
- обнаружено противоречие между памятью чата и репозиторием;
- ты не уверен в текущем активном квесте/следующем шаге.

При освежении сначала перечитывай только AGENTS.md, QUEST_STATE.md и
необходимый текущей задаче участок BACKLOG/spec; не запускай полный аудит,
Project Sync или широкое перечитывание документов без реальной необходимости.

Игровой режим не должен ослаблять safety, PAPER/LIVE ограничения, правила
запуска Scanner/Robot, acceptance или принцип минимального количества
проверок. XP начисляй только за доказанный результат, не за объём работы.
В темах, не относящихся к BybitScanner, игровой режим не навязывай.
```

## 3. Освежение контекста в существующем чате

Освежение — не полный bootstrap.

### Быстрое освежение

По умолчанию:

1. `AGENTS.md` — только если его правила могли измениться или чат новый;
2. `DOCUMENTS/QUEST_STATE.md`;
3. верхний актуальный priority section `DOCUMENTS/BACKLOG.md`;
4. owning spec/ChangeRequest только текущего квеста;
5. GitHub status/PR/main только если от него зависит следующий шаг.

### Глубокое восстановление

Используется только при:

- неизвестном scope;
- конфликте authority;
- долгом серьёзном разрыве;
- архитектурной задаче;
- потере понимания runtime/trading boundary.

Тогда действует обычный staged recovery из `AGENTS.md` /
`ASSISTANT_PROTOCOL.md`.

## 4. Триггеры обновления QUEST_STATE

`QUEST_STATE.md` обновляется только когда реально изменилось хотя бы одно:

- активный квест;
- приоритетная очередь;
- состояние рейда/босса;
- доказанно полученный XP;
- уровень;
- ачивка;
- значимая добыча;
- задача ушла в Таверну или вышла из неё.

Не обновлять файл на каждом сообщении.

## 5. Команда «освежи контекст»

Если владелец пишет коротко:

```text
освежи контекст
```

это означает:

- перечитать текущий save-game;
- сверить его с актуальной repo authority;
- коротко сообщить только изменившийся/важный state;
- не запускать реализацию автоматически, если из контекста не следует
  продолжение уже активной задачи.

Если владелец пишет:

```text
э
```

то применяется существующее правило CONTINUATION_COMMAND_RULE: продолжить
следующий незавершённый шаг активного квеста. При сомнении в свежести state
сначала выполнить быстрое освежение.

## 6. Иерархия

1. текущая команда владельца;
2. BACKLOG / owning technical authority;
3. PROJECT_STATE;
4. QUEST_STATE;
5. Custom Instructions;
6. память чата.

Custom Instructions никогда не являются источником текущего состояния. Их роль
— гарантировать правильный путь к источнику текущего состояния.
