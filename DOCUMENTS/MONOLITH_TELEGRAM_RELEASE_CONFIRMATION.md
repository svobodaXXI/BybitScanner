# Подтверждение релиза в Telegram — MONOLITH / #640

Статус: код подготовлен к проверке; **не активировано**. Один существующий бот, Cloudflare Gateway и getUpdates consumer. Отдельный адаптер подтверждения не исполняет релизы: после независимой проверки согласия передаёт только одноразовый typed grant существующему vps_owner_control → paper_maintenance. Диагностический протокол не получает новых полномочий.

## Одно подтверждение

Недоверенный запрос содержит version=1, operation (update или update-and-start), owner_request_id (32 hex), expected_installed_sha и target_sha (полные 40 hex), issued_at/expires_at (unix seconds, срок ≤900 секунд). Фиксированный вход: ветка owner-release-proposals, .github/owner-release-request.json. Наличие файла, GitHub PAT и диагностическая подпись не являются согласием. Отдельная ветка создаётся после review, не содержит ключей. Произвольные команды, LIVE, STOP и escalation исключены.

Root-only адаптер проверяет точный установленный release, формирует текст с обоими SHA, UUID, явным режимом и сроком действия, сохраняет случайный nonce и hash точного текста до единственной отправки через существующий Gateway. Сохраняет подтверждённый Telegram message_id. Неподтверждённая отправка не повторяется и не допускает callback. Обычный мониторинг продолжает единственный getUpdates; Gateway при отдельном opt-in подписывает только реальный upstream callback владельца в личном чате, связанный с bot/message ID, точным текстом, nonce и временем. Обычный VPS бот может передать непривилегированный файл с подписью, но не может подписывать receipt, запрашивать sudo или сам запускать монолит. Root проверяет подпись, точный сохранённый challenge, freshness, текущий SHA и независимость ключей, расходует challenge до отправки одноразового grant. Отказ/просроченный запрос не исполняются. Неопределённый submit не повторяется. После отправки UUID наблюдается через уже существующий signed owner_status; SUBMITTED не равно VERIFIED_PAPER_READY.

## Защитные ворота перед эксплуатацией (отдельное разрешение владельца)

- Согласованная публикация Gateway с проверкой actual Cloudflare deployment, затем отдельное подтверждение существующего Telegram маршрута и независимой подписи. Не запускать второй бот/poller и не использовать transport bearer как approval key. Доверенный signer Gateway и подлинность bot token должны быть подтверждены; при подозрении на компрометацию тот же канал не активировать до устранения причины. RISK-MONOLITH-01 остаётся открытым.
- Независимый Ed25519 seed Gateway (OWNER_RELEASE_CALLBACK_SEED, 64 hex) хранить только в защищённом Cloudflare окружении, OWNER_RELEASE_CALLBACK_ENABLED=1 только при согласованной активации. На VPS — только его public key, отдельный approval seed, не совпадающий с диагностическими и Gateway ключами. Секреты не помещать в GitHub, чат, аргументы команд или журналы. Обычный shared gateway bearer не подписывает разрешения; он всё ещё может нарушить доступность Telegram. Telegram account/Gateway deployment — доверенная граница подписи.
- Root-owned 0700 /etc/bybitscanner/owner-release, config.json 0600: enabled (bool, первоначально false), owner_id и bot_id (строки numeric ID), audience (32 hex), callback_public и approval_seed (64 hex). Совпадение owner_id с действующим Gateway route, независимость всех четырёх ключей. Existing protected diagnostic config supplies issuer/responder pins. Не переиспользовать ключи.
- Root-owned 0700 /var/lib/bybitscanner-owner-release; pending.json 0600 с {"pending":null}; подкаталоги prompts и grants 0700, каждый однократно и явно initialized существующим GrantLedger.initialize(). Ledger не пересоздавать, не очищать и не считать отсутствие receipt разрешением повторить. /var/lib/bybitscanner-owner-release-inbox — отдельный 0700 каталог владельца bybitscanner, непривилегированный и недоверенный; root читает только bounded, exact nonce file и проверяет подпись. Не переносить в tracking tree или общую PAPER DB.
- Перед любым включением конфигурации выполнить штатную read-only проверку `python -m tools.owner_release_telegram_runtime --preflight` через **отдельно разрешённый защищённый канал**. Она проверяет точный установленный SHA и blob manifest, root-owned code/конфигурацию, идентичность обоих установленных unit-файлов версии, начальное pending=null, нерасходуемые initialized journals, непривилегированный inbox, диагностические ключи и Gateway route. Выдаёт `HOST_PRECHECK_OK_DISABLED` либо `HOST_PRECHECK_OK_ENABLED` только для локальных предпосылок, **не** доказывает публикацию Cloudflare, реальное нажатие владельца или READY Робота; при неопределённости возвращает BLOCKED без изменения файлов/служб. Проверка не создаёт конфигурацию и не включает таймер.
- Новые service/timer **не включены** в обычную подготовку systemd. Сначала отдельное проверенное provisioning действие на согласованном exact release должно установить эти unit-файлы, защищённое состояние и конфигурацию без затрагивания Scanner/Robot. Только затем отдельный owner opt-in для таймера. Отзыв через root-owned enabled=false; никаких автоматических grant/перезапусков. Не удалять receipts. Полностью остановленный обычный Telegram worker не предоставляет возможности нового подтверждения; восстановление остаётся в прежнем owner-controlled START, не создаётся второй poller.
- CI, отдельный merge, отдельный Gateway/VPS rollout; затем owner-only подтверждение реального запроса и коррелированный signed exact UUID/action/SHA outcome. Не останавливать работающий PAPER ради разработки. До реального roundtrip и отдельной owner acceptance сквозная автоматизация не принята.
