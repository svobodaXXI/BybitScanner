# BybitScanner — план системного аудита и ускорения процесса
Дата: 2026-10-09  
Статус: **план, не разрешение на реализацию**  
Источник: поручение владельца провести системный аудит GitHub, сопоставить с практиками зрелых проектов и разработать план.  
База документа: `stable/adfb50b-forward`, `5435f29681052cc1f7a0e0b2d750d4dee08e100b`.

## 1. Цель и границы

**Цель:** сократить время от решения владельца до проверяемого полезного результата Scanner/PAPER Robot, сохранив функциональность, safety-gates и владельческий контроль runtime.

**Вне scope:** LIVE; изменение стратегических параметров и риск-лимитов; запуск Scanner/Robot агентом; миграция DB; удаление dirty worktrees #396/#397; автоматическое переключение runtime с stable на main; широкая инфраструктурная переделка ради метрик; изменение приоритетов без команды владельца.

**Эксплуатационный приоритет:** первый штатный PAPER-запуск на ноутбуке и затем Robot Stability → Geometry Quality. Этот аудит не добавляет эксплуатационного блокера без доказанного критического нарушения обязательных gates.

5. Handoff владельца сообщает RESTORE PASS и STOPPED на ноутбуке, но результат первого реального PAPER-запуска ещё не получен. Это именно **сообщённый checkpoint**, а не свежая проверка хоста через GitHub.

## 3. Вопросы аудита (с доказательствами, не предположениями)

### A. Authority / Git / контекст
- Установить назначение `main`, `stable`, acceptance и dirty worktrees по фактическим PR, branch policy и документации; описать безопасный путь будущих изменений без автоматического слияния.
- Найти **один** существующий актуальный индекс следующего действия (предпочтительно актуальный раздел `BACKLOG` согласно `AGENTS.md`); выявить лишь подтверждённые противоречия с `QUEST_STATE` и `PROJECT_STATE`.
- Проверить, какие шаги локальной синхронизации действительно нужны при переходе GitHub ↔ Codex; не повторять preflight при read-only анализе.

### B. Производственный цикл изменений
- По выборке последних 15–30 PR восстановить: задача → код → targeted validation → CI → merge/backport → owner PAPER acceptance; отделить объединённые фиксы от повторных неудачных итераций.
- Классифицировать задержки: требования, очередь, ожидание, CI, дополнительные проверки, контекст, интеграция веток, ручные действия владельца.
- Отметить уже исправленные проблемы и реальные повторные циклы; не считать число PR само по себе неэффективностью.

### C. Scanner / Robot / observability
- Сопоставить критический путь `signal → candidate → admission → execution → protection → close/reconciliation → Telegram` с текущими кодом и incident evidence.
- Внимание к синхронному I/O в owner-thread, очередям ingress, idempotency, дедлайнам и причинно-следственным диагностическим следам; проверить эффект серии backport #394/#396–#402/#424–#435 перед новой оптимизацией.
- Разделить безопасность, продуктовые дефекты и чисто эксплуатационные улучшения. Никакого запуска runtime, внешнего API trading и прямой правки PAPER DB для аудита.

### D. Архитектура и тесты
- Построить карту ownership, границ модулей и реально медленных тестов/CI шагов из репозитория и доступных артефактов.
- Различать быстрые targeted checks, обязательные safety gates и единственную owner-managed полную Scanner Telegram-приёмку. Не подменять последнюю офлайн-реплеем или одиночной карточкой.

## 4. Практики для сравнения (не готовые рецепты)

- **Continuous Integration / small batches:** короткие PR и ранняя интеграция; Martin Fowler, https://martinfowler.com/articles/continuousIntegration.html
- **Deployment Pipeline:** дешёвые узкие проверки раньше дорогих, без исключения обязательных gates; https://martinfowler.com/bliki/DeploymentPipeline.html
- **Trunk-Based Development:** ограничение срока жизни feature branches; https://trunkbaseddevelopment.com/ — только после доказанного понимания назначения stable/main; не предлагать немедленное объединение веток.
- **DORA metrics:** измерять lead time и изменение доли неуспешных изменений, но не использовать метрики как повод добавлять отчётную бюрократию; https://dora.dev/guides/dora-metrics-four-keys/

Каждую практику принимать только с указанием локального дефекта, ожидаемой экономии, стоимости внедрения, риска и способа проверки результата.

## 6. Метрики эффекта

Базовые показатели извлекать из фактических временных отметок PR/CI/issue/owner acceptance, если доступны:
- lead time: решение → принятие работающего результата;
- PR cycle: открытие → merge и число повторных CI/proof итераций;
- ручные действия владельца на один принятый результат (отделяя обязательный запуск и визуальную приёмку);
- доля найденных после merge дефектов / повторные инциденты;
- для Scanner/Robot только при надёжных логах — signal-to-admission / admission-to-protection / close-to-reconciliation latency.

Не устанавливать процентные обещания до измерения baseline. Победа — сокращение подтверждённых потерь **без** регрессии безопасности и качества.

## 7. Правила проведения и точка возврата

1. Принимать текущую команду владельца выше исторического квеста; исходить из `AGENTS.md`, верхнего актуального приоритета `BACKLOG`, затем owning authority. `QUEST_STATE` — проекция, а не самостоятельный маршрут.
2. Анализировать GitHub read-only. Любые патчи — отдельный согласованный узкий scope, с проверкой соответствия локальному checkout до мутации.
3. Не расширять исследование в постоянный поток PR. Зафиксировать не более трёх наиболее доказательных улучшений; всё остальное отложить.
4. PAPER runtime и владелец: запуск только с существующего ярлыка, одновременный Telegram Monitoring на ПК/ноутбуке запрещён. `CELOUSDT reconciliation_required` — известный сохранённый случай, не новый автоматический блокер.
5. После аудита вернуться к первому PAPER-запуску на ноутбуке и Robot Stability → Geometry Quality. XP и достижения не начислять за один документ или аудит.

## 8. Definition of Done этого рейда

**Аудит завершён**, когда есть: карта authority/веток, evidence-linked карта критического пути, измеренная или явно ограниченная по данным таблица задержек, максимум три конкретных предложения с оценкой эффекта/риска и зависимостями. **Реализация завершена** только после отдельных подтверждённых изменений и их обязательной приёмки. Документ сам по себе не означает ни устранения дефектов, ни PAPER READY.
