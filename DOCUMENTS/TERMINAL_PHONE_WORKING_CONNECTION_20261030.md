# Рабочая схема: Telegram → защищённый мобильный Terminal на VPS

**Подтверждено владельцем 2026-10-30:** на телефоне через Telegram открывается реальный Workspace/Terminal. Это пользовательская приёмка открытия интерфейса, **не** доказательство проверки каждого торгового действия, устойчивости при долгой эксплуатации или готовности LIVE. LIVE запрещён.

## Зафиксированная цепочка и адреса

1. На телефоне Telegram → бот **BybitCleanScanner** → команда `/terminal` → inline-кнопка «Терминал» (`web_app`).
2. Telegram Mini App открывает **`https://83.217.213.181/login`**, значение `BYBITSCANNER_WORKSPACE_URL` **в Telegram-службе VPS**.
3. HTTPS (прямой внешний TCP 443 VPS, **без Tailscale, Windows, SSH-туннеля, домена или внешнего прокси**) завершается на Nginx VPS. Порт 80 используется только для ACME HTTP-01 challenge; обычным HTTP-содержимое Терминала не выдаётся.
4. Публичный Nginx :443 направляет трафик **только** на защищённый loopback Nginx **127.0.0.1:8081**. Защищённый Nginx для `/` и `/api/` использует `auth_request /_auth` → локальный Python auth sidecar **127.0.0.1:8091**.
5. Страница `/login` получает Telegram `WebApp.initData`. Sidecar проверяет HMAC Telegram, время `auth_date` и разрешённый **числовой Telegram user ID**. При успехе выдаёт защищённую ограниченную по сроку сессию (Secure, HttpOnly, SameSite=Strict). Далее разрешается загрузка существующего Workspace; `/api/` проксируется к локальному PAPER backend **127.0.0.1:8765**. Legacy локальный Terminal **127.0.0.1:8080** не публикуется.
6. Входящие/исходящие Telegram-сообщения передаются по отдельному, ранее подтверждённому HTTPS Gateway **https://bybitscanner-telegram-gateway.vercel.app**. Это транспорт Telegram, **не** прокси веб-Терминала и не владелец торговли. У Telegram-службы ровно один потребитель `getUpdates`.

### Сертификат и автоматическое продление (отчёт VPS-оператора)

- Certbot **5.9.0**, Let's Encrypt **shortlived** сертификат с IP SAN для `83.217.213.181`.
- Автопродление: systemd timer **enabled/active**; deploy-hook проверяет Nginx и делает reload.
- **`certbot renew --dry-run --no-random-sleep-on-renew` — PASS** по отчёту оператора. Без последнего флага штатная случайная задержка составляла **446 секунд**, ошибочно воспринималась как зависание.
- Поскольку сертификаты shortlived, состояние продления критично для долговременной работы внешнего UI. Недоступность TLS не должна затрагивать автономные PAPER Robot/STOP/TAKE; данное разделение требует отдельного runtime-доказательства.

## Фактическая приёмка

- По отчёту VPS-оператора до телефонного E2E: Nginx слушает `0.0.0.0:443`, firewall VPS не блокирует INPUT 443, внешний TCP 443 доступен из Испании, Португалии, Сербии, Сингапура и Турции, `/login` возвращает HTTP 200 по валидному TLS приблизительно за 0,15 с.
- По отчёту оператора проверены отказ без авторизации и блокировка прямого доступа к `/api/`; Telegram-служба перезапущена с установленным `BYBITSCANNER_WORKSPACE_URL`. Backend не перезапускался.
- Первое открытие ссылки кнопкой в Telegram на телефоне завершилось **`ERR_TIMED_OUT`**. Причина **не доказана**: нельзя заявлять установленную блокировку мобильной сети или дефект Telegram WebView.
- Затем владелец открыл `https://83.217.213.181/login` в обычном браузере телефона и увидел «Откройте Терминал через Telegram» — это **ожидаемый отказ авторизации вне Telegram**, не сбой.
- После возврата в Telegram владелец повторно нажал кнопку «Терминал» — **Workspace/Terminal успешно открылся на телефоне**. Это подтверждённый конечный результат; надёжность первого открытия остаётся наблюдаемым ограничением.

## Как восстановить доступ без новой разработки

1. **Не начинать с перестройки архитектуры.** Сначала проверить, что `/terminal` выдаёт ссылку, а `https://83.217.213.181/login` извне отвечает по TLS. Открытие вне Telegram должно показывать предложение открыть через Telegram, а не обходить авторизацию.
2. Если браузер телефона выдаёт `ERR_TIMED_OUT`, но внешний HTTPS работает: повторить открытие через Telegram после одного прямого открытия `/login` в браузере; если не помогло — различить сеть Wi-Fi/мобильную сеть/Telegram WebView **минимальными** проверками. Не обвинять оператора без доказательств.
3. Если HTTPS недоступен везде: проверить только public :443, Nginx, firewall VPS/провайдера и срок сертификата; не менять торговый backend.
4. Если истёк сертификат: проверить таймер Certbot и результат renewal/dry-run **без случайной задержки**; исправлять только сертификат/перезагрузку Nginx, не трогая PAPER.
5. Если `/login` открывается, но подписанная сессия не создаётся: проверить auth sidecar :8091, `auth_request` и защищённые переменные окружения, не выводя токены/секреты в логи. Запрос без действительной подписи должен быть отклонён.
6. Если не приходит кнопка: отдельно проверить единственную Telegram-службу, Gateway и значение `BYBITSCANNER_WORKSPACE_URL`. Не запускать второго `getUpdates` consumer.
7. Любое обнаруженное изменение кода/репозиторной конфигурации делать **через GitHub PR**; Codex лишь оператор VPS. Не заменять работающие настройки вслепую, сохранять точечный откат.

## Непреложные границы

- Публичны только предназначенные для HTTPS/ACME порты **443/80**; **8080, 8081, 8091, 8765** остаются loopback и не открываются извне.
- Не публиковать `/api/` напрямую, не отключать проверку `initData`, `auth_date`, owner ID, cookie или Nginx `auth_request`; отказ sidecar — **fail closed**.
- **Никаких секретов в GitHub**: бот-токен, Gateway shared secret, ключ подписи сессии, SSH-ключи и файлы сертификата/приватный ключ — только в защищённых настройках хоста/провайдера.
- Работа внешнего интерфейса **не** должна управлять жизненным циклом Robot/Scanner; backend, Admission, STOP/TAKE, PAPER DB и PAPER_AUTO не изменять без отдельного разрешения. LIVE запрещён.
- Изменение публичных портов, TLS, авторизации или торгового runtime требует отдельного разрешения владельца.
